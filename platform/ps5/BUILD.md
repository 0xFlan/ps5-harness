# PS5 agent build and package

Status: **the real agent cross-builds, links and validates on this Mac; nothing
has run on a console.** `make -C platform/ps5` produces `eboot.bin` from the
same `src/*.cpp` sources as the host harness, linked against PacBrew's static
libcurl/OpenSSL, plus `harness.elf`, a real SFO and a real icon. P2's boot
criterion and every P3 capability claim still require a PS5.

The package contains:

- `eboot.bin` — a fake SELF (`4f15 3d1d`) packed from `harness.elf` by the
  SDK's `make_fself.py`, for a loader that installs a title.
- `harness.elf` — the real x86-64 FreeBSD ELF, for a loader that takes raw ELF
  (elfldr on port 9021). It is the agent, not the bring-up probe.
- `sce_sys/param.sfo` — a real SFO binary generated by
  `platform/ps5/tools/make_sfo.py`.
- `sce_sys/icon0.png` — a real 512x512 RGBA PNG generated by
  `platform/ps5/tools/make_icon.py`.
- `sce_sys/param.json` — JSON metadata some installers stage instead of an SFO.

`make -C platform/ps5 bringup` still builds the P2 resource-probe ELF (without
libcurl) for diagnostics. It is not part of the package and is not the artifact
the checklist asks you to install.

## What the agent binary contains

Every production source file is compiled for the target:

```
src/agent.cpp  src/core.cpp  src/endpoints.cpp  src/http.cpp  src/json.cpp
src/main.cpp   src/paths.cpp src/plugins.cpp    src/policy.cpp
src/pool.cpp   src/resources.cpp src/runtime.cpp src/secrets.cpp src/sha256.cpp
platform/ps5/console_compat.cpp
```

The static dependencies come from the PacBrew v0.41.1 image:

| Component | Version | Licence |
|---|---|---|
| libcurl | 8.18.0 | curl licence (MIT/X derivative) |
| OpenSSL | 3.5.2 | Apache-2.0 |
| zlib | 1.3.2 | zlib licence |
| zstd | 1.5.6 | BSD-3-Clause |
| libpsl | 0.21.5 | MIT (bundled Public Suffix List data MPL-2.0) |

They are linked statically; a distributable build must carry their licence
notices. The target link is:

```
prospero-clang++ ... -DPS5H_PS5_TARGET -DCURL_STATICLIB \
  -Wl,--no-pie -Wl,--wrap=fcntl \
  src/*.cpp console_compat.cpp \
  -lcurl -lpsl -lssl -lcrypto -lzstd -lz -ldl -pthread
```

`-Wl,--no-pie` is required because `make_fself.py` accepts `ET_EXEC`, not
`ET_DYN`. `-Wl,--wrap=fcntl` routes curl's socket-flag calls through
`console_compat.cpp`.

## Dependencies

The payload SDK is v0.45 (zip sha256
`5fac64093d0e3e69f2584ce7935f24f703f622d9681f1495c85b9f00d1291a2c`), built
with LLVM 23.1.4 on macOS 26.6.2 (arm64). The agent needs the SDK's libc++,
libdl and pthread plus the PacBrew archives.

Fetch both under `.deps/` (gitignored):

```bash
mkdir -p .deps && cd .deps
curl -fsSLO https://github.com/ps5-payload-dev/sdk/releases/latest/download/ps5-payload-sdk.zip
unzip -q ps5-payload-sdk.zip
cd ..

mkdir -p .deps/pacbrew && cd .deps/pacbrew
curl -fLO https://github.com/ps5-payload-dev/pacbrew-repo/releases/download/v0.41.1/ps5-payload-dev.tar.gz
shasum -a 256 ps5-payload-dev.tar.gz
# e811bc2e4676c5bb7f80a8fe928d2985dce599996a5ca6b54da3e72699287887
mkdir -p root && tar -xzf ps5-payload-dev.tar.gz -C root
cd ../..
```

The PacBrew image is 227,961,140 bytes compressed and extracts under
`root/opt/ps5-payload-sdk/target/user/homebrew/`. The build uses explicit
include/lib paths rather than `pkg-config`, so no host `pkg-config` is needed.

```bash
export PS5_PAYLOAD_SDK="$PWD/.deps/ps5-payload-sdk"
export LLVM_CONFIG=/opt/homebrew/opt/llvm/bin/llvm-config
make -C platform/ps5
```

Without the SDK or PacBrew, `package` fails with the missing path. The
generated assets still build on a host-only checkout:

```bash
make -C platform/ps5 host-assets
```

## Console glue

`platform/ps5/console_compat.cpp` is compiled only into the target:

- **CA bundle** — `ps5h_console_ca_bundle()` prefers `PS5H_CA_BUNDLE`, then
  `/<sandbox word>/common/cert/CA_LIST.cer` (using
  `sceKernelGetFsSandboxRandomWord()`), then
  `/system/common/cert/CA_LIST.cer` for an elevated title. The console's
  `CA_LIST.cer` is a PEM file OpenSSL can read directly; verification is never
  disabled.
- **Non-blocking sockets** — `ps5h_console_nonblocking()` sets the console's
  `SO_NBIO` (`0x1200`), which `CURLOPT_SOCKOPTFUNCTION` applies to every socket.
  curl's own `fcntl(O_NONBLOCK)` does not do this on the console.
- **`fcntl` wrapper** — `__wrap_fcntl` accepts `FD_CLOEXEC` when the sandboxed
  libc returns `EINVAL`, and maps `O_NONBLOCK` to `SO_NBIO`. Files and pipes
  stay on the real call; `ENOTSOCK` is treated as a harmless file flag.

The SDK's payload libc already exports `getaddrinfo`, `freeaddrinfo`,
`gethostbyname`, `getnameinfo`, `fnmatch`, `gmtime_r`, `getpwuid_r`, `pipe2`,
`openlog`, `closelog`, `dladdr` and `if_nametoindex`, so the libc stand-ins that
native titles need were not required for this link. The link is the proof of
symbol resolution; DNS/TLS behaviour on the console is not.

## Runtime scaling

`src/resources.cpp` probes the process, `src/runtime.cpp` turns the probe into
a budget, and `src/pool.cpp` executes one turn's tool calls across it:

- **Workers** — `workers = cpu_online`, reduced only when the fd limit cannot
  support 8 descriptors per worker plus 24 for the process. `raise_fd_limit()`
  first raises `RLIMIT_NOFILE` soft to the loader's hard limit.
- **Buffered responses** — `max(1 MiB, visible_memory / 16)`, using available
  memory when the platform reports it, total memory otherwise, and further
  capped by `RLIMIT_AS` and `RLIMIT_DATA` when finite. The old fixed 4 MiB
  ceiling is gone; the cap is a share of measured memory.
- **File reads** — `min(buffered, 4 MiB)`: the model context, not console
  memory, is the binding constraint on text sent to the provider.
- **Downloads** — capacity is the destination filesystem's free space minus a
  1% reserve capped at 64 MiB, and also bounded by `RLIMIT_FSIZE` when set.
  The streaming client stops when written bytes would exceed it.
- **Deadlines** — each tool call keeps its own deadline; a hung handler is
  abandoned, not joined.

`harness --resources` prints the probe and budget on the host;
`tests/resources_test.cpp`, `tests/runtime_test.cpp` and the parallel tool-call
case in `tests/e2e_agent_test.cpp` assert the scaling rules.

## Build output and host validation

```bash
make -C platform/ps5
./build/ps5_package_test .deps/ps5-build/PHAR00001
make test
```

`make test` regenerates the SFO and icon, then runs `build/ps5_package_test`,
which requires `eboot.bin` and `harness.elf` in full mode. It parses the SFO
from disk, walks the PNG chunks and CRCs, checks the fSELF magic and the ELF
class/type/machine, and (when present) the diagnostic `bringup.elf`. A host-only
checkout runs in `--assets-only` mode.

## On a console

Record the environment first: host OS and LLVM version, SDK zip sha256, PacBrew
version and bundle sha256, console firmware/exploit version, and the artifact
build id.

### Load the ELF

With `ps5-payload-elfldr` listening on 9021:

```bash
nc -w 30 <console-ip> 9021 < .deps/ps5-build/PHAR00001/harness.elf
```

The agent appends diagnostics to `/data/ps5-harness-agent.log`, then
`/user/homebrew/ps5-harness-agent.log`, then `./ps5-harness-agent.log`
(`--log <path>` overrides). The first lines contain `build=… title=PHAR00001`,
the resource probe, and the runtime budget. With no prompt, it logs
`no prompt supplied; usage printed` and exits 2; this is a CLI, not a title
launcher.

To run a turn, pass `--config` and `--prompt` through a loader that preserves
argv, and provide the model key in the environment named by the config. The
key is never read from the config file.

### Install as a title (untested sequence)

The title's `eboot.bin` is the agent, but a title launch supplies no argv, so it
will print usage until a launch path for arguments/config exists. This sequence
mirrors the SDK's `install_app` staging over FTP and has **not been run**:

```bash
export PS5_HOST=<console-ip>
curl -Q "MTRW" ftp://$PS5_HOST:2121
curl -Q "MKD /system_ex/app/PHAR00001"         ftp://$PS5_HOST:2121 || true
curl -Q "MKD /system_ex/app/PHAR00001/sce_sys" ftp://$PS5_HOST:2121 || true
curl -Q "MKD /user/app/PHAR00001"              ftp://$PS5_HOST:2121 || true
curl -Q "MKD /user/app/PHAR00001/sce_sys"      ftp://$PS5_HOST:2121 || true

curl -T .deps/ps5-build/PHAR00001/eboot.bin         ftp://$PS5_HOST:2121/system_ex/app/PHAR00001/
curl -T .deps/ps5-build/PHAR00001/sce_sys/param.sfo ftp://$PS5_HOST:2121/user/app/PHAR00001/sce_sys/
curl -T .deps/ps5-build/PHAR00001/sce_sys/icon0.png ftp://$PS5_HOST:2121/user/app/PHAR00001/sce_sys/
```

## What this does not prove

- That the fake SELF is accepted by the loader or that the title launches.
- That the SFO key set and `--paid`/`--ptype` values suit your firmware.
- That the console clock is correct, that `libcurl`'s DNS path works there, or
  that `CA_LIST.cer` is found at either probed path.
- That `dlopen` loads a plugin `.so` in a title.
- That any write succeeds under `/data/homebrew`, USB or the app folder.
- That the file logger can create `/data/ps5-harness-agent.log`.
- That a title launch can receive the `--config`/`--prompt`/key it needs.

Those are console checks in `docs/HARDWARE-CHECKLIST.md`. P3's TLS, `dlopen`
and elevated-write criteria are all still unclaimed.

## Known risks at this stage

| Risk | Symptom | First check |
|---|---|---|
| Fake SELF rejected | Title absent or system error on launch | loader docs, `--paid`/`--ptype` |
| SFO key set differs | Install fails or no shell entry | compare a working homebrew title |
| Sandbox denies log file | No `/data` log, but payload ran | own folder vs `/data` vs USB |
| DNS resolver differs | `CURLE_COULDNT_RESOLVE_HOST` (-10006) | kernel log, `getaddrinfo` result |
| CA path not found | `CURLE_SSL_CACERT_BADFILE` (-10077) | both CA paths, `PS5H_CA_BUNDLE` |
| Console clock wrong | certificate not yet valid / expired | clock before certificates |
| `fcntl` wrapper insufficient | `fcntl set CLOEXEC: Invalid argument` | error buffer from curl |
| `dlopen` unavailable | plugin load fails, built-ins work | exact `dlerror()` |
